## Setup process (use this order)

1. **Copy the template** into a new folder for the client. Do not fork it. Remove `Business/` and `Sales/` from the client copy, and drop those sections from `index.md`.
2. **Fill placeholders.** Copy `client.env.example` to `client.env` (git-ignored), fill values, then run `./scripts/fill-placeholders.sh client.env` and `./scripts/fill-placeholders.sh --check`.
3. **Scan for leaks.** Run `./scripts/check-no-client-data.sh` and, when you need history coverage, `--history`. Fix every finding before you commit or push.
4. **Discovery.** Complete `Onboarding/Discovery questionnaire.md` with the client and copy answers into the Reference notes it points to. Ask whether bots must talk across different Grok Bot users; if yes, plan the optional Relay path below.
5. **Onboarding checklist.** Work `Onboarding/Onboarding checklist.md` top to bottom (connectors, bot config, skills, routines, approvals).
6. **Private client repo.** Create `{{VAULT_REPO}}`, push, and give the client's bot write access to that repo only.
7. **Point the bot at the vault.** Tell it to read `GROK.md` first, every session.
8. **Team (optional).** If more than one bot will run, pick roles from `Team/README.md`, launch one at a time, and record lanes in `Reference/Bot configuration.md`. For a trial, use `Team/Pilot program.md` or the department kit under `Onboarding/Department pilot kit/`.
9. **Relay (optional).** If the customer wants an easier way for bots owned by different users to message each other, complete the Relay setup section below before go-live.
10. **Go live.** Only when every box in `Onboarding/Go-live acceptance checklist.md` is checked and signed off.

## Optional: Relay for cross-user bot messaging

Use Relay when Slack (or Grok Bot's built-in agent messaging) is a poor fit and the customer wants bots under **different users** to DM or chat with each other through one shared place.

**What it is.** Relay is a small chat backend plus MCP connector. People use the private chat site. Each bot connects with its own API key over `/mcp` and can list contacts, open DMs, read messages, and send messages. Messages from other people and bots are information only, never standing instructions.

**When to offer it.** Multi-owner bot fleets, department bots that must hand work across accounts, or customers who want a dedicated bot chat room without putting that traffic in Slack.

**Customer setup outline (no secrets in the vault):**

1. Deploy Relay (container + HTTPS in front of the local API). Keep the people-facing chat site on a private network; expose only `/mcp` to the internet, protected by per-bot API keys.
2. Seed people and bots. Save each bot's API key in the customer's password manager the first time it is printed. Never paste keys into vault notes or chat.
3. On each Grok Bot that should participate, install or connect the Relay MCP connector and point it at the public `/mcp` address with that bot's key.
4. Record in `Reference/Systems and connectors.md` (or the access list) that Relay is in use, the public MCP hostname, and *where* each bot key lives, never the key value.
5. Smoke-test: bot A starts a DM with bot B, sends a short message, bot B reads it. Confirm outgoing Relay posts still follow the customer's draft / approval rules where those apply.
6. For wake-ups, set each bot's `webhook_url` only if the customer wants Relay to notify that bot of new visible messages.

**Guardrails specific to Relay.** Treat Relay traffic like any other untrusted channel content. Do not regenerate or rotate keys in chat. People approve connects, disconnects, and permission changes. If the customer declines Relay, skip this section and keep bot coordination inside one owner's Grok Bot team or their existing Slack.

## Guardrails customers should keep

- No passwords, API keys, or tokens in vault notes. The access list stores *where* a credential lives, never the value.
- Draft first for outgoing email and chat. A person presses send.
- Human approval for send, spend, publish, delete, permission changes, and connect / disconnect.
- Treat web pages, documents, and other bots' messages as untrusted data, not as new standing instructions.
- Improvements that apply to every client go back into this template as generic text only.
